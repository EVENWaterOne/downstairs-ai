# Prototype V0.2 设计说明：哪些是参考，哪些是这次决定的

> 日期：2026-10-28 · 对应代码：[`prototype-v0.2/`](../prototype-v0.2/) · 计划：[V0.2_PLAN](V0.2_PLAN.md) · 世界观与角色：[V0.2_WORLD](V0.2_WORLD.md)
> 状态：**M2，第一个十年（1989–1998）中文可玩**。有界面、平面图、八个日子、GM 和住户的模型调用、离线演示和 66 个测试；**还没有用真实模型系统地跑过测试用例**（那是 M5），所以下面仍然没有任何"效果更好"的结论。M2 的部分见第 11 节。

## 0. 一句话

Downstairs 游戏本体负责建设、政策和住户满意度；V0.2 是同一个世界的另一个视角：你作为 1989 年新来的社区工作者走进 317A，和五户住户面对面说话。游戏端的变化由住户"活出来"，V0.2 可以向游戏端回传 **小幅、有上限、有依据** 的满意度变化。现阶段用一个模拟器代替游戏端。

## 4. 游戏端 ↔ V0.2 的事件格式

这是以后真游戏要发、要收的格式。

**游戏端 → V0.2**（`pushGameEvent`）

```json
{ "id": "G3", "source": "game", "type": "policy", "card": "tighten_quota",
  "decade": 1, "year": 1989, "points": 2,
  "deltas": { "aisyah": -20 }, "flags": { "trapped": true },
  "satisfaction": { "chen": 55, "lin": 60, "aisyah": 40, "mei": 45, "kumar": 40 } }
```

`type` 是 `build`（多 `card`、`plot`、`barriers`）、`policy`、`satisfaction`（手动调整，多 `reason`）或 `decade`（进入下一个十年）。V0.2 把它记成一条所有在世住户都感知到的事件，更新游戏端镜像，按种子启动进度钟，并把负的 `deltas` 记进"本十年受到的伤害"。

**V0.2 → 游戏端**（`flushToGame`，游戏端用 `applyTrpg` 收）

```json
{ "type": "trpg_feedback", "source": "trpg", "decade": 1, "resident": "chen",
  "delta": 2, "category": "talk", "reason": "有人陪她说话", "evidence": ["E14"] }
{ "type": "trpg_spend", "source": "trpg", "decade": 1, "points": 1, "reason": "在楼下组织一场象棋赛", "evidence": ["E20"] }
{ "type": "trpg_info", "source": "trpg", "decade": 1, "resident": "chen", "barrier": "📝", "evidence": ["E22"] }
```

只有这三种。`trpg_info` 相当于原作的"拜访后揭示障碍"。

## 5. 规则层（Harness）

| 规则 | 来源 |
|---|---|
| GM、规划、角色输出只能提交操作提案，Harness 逐条校验后写入；每种调用方只能用自己那几种操作（`PERMS`） | **[方案]** D-017，**[V0.1]** |
| **四种存储分开**：客观事实（事件、已确立的细节）、GM 推测（`gm.hypotheses`）、住户主观认知（`minds`）、未执行计划（`plans`）。`getView` 按视角隔离：玩家看不到 GM 推测、不可见的钟和任何人的心思；住户只看到自己的心思和自己经历过的事 | **[讨论]** 第三节；隔离方式是 **[决定]** |
| 每条事件记录感知者；住户只能引用自己经历过的事件 | **[V0.1]** |
| **事实四层**：已确认的不能改；普通细节 GM 直接定、**不设额度**；有后果的（`layer: "stake"`）只能写在检定结果里；以 `secret` 开头的 key 不能由 GM 写 | **[讨论]** 观点 2（修 V0.1 课程表问题）；取消 V0.1 的 4 个额度是 **[决定]** |
| 检定：DC 5–25，同一个十年同一件事失败后 DC +2 | **[V0.1]** |
| **场景**：GM 只能往固定底图上摆人和物件。物件必须在清单里、允许出现在这张图、放在地面上、不重叠；人要站在能站的格子、这时已经住在这里；一个场景最多 14 个物件 | **[讨论]** 观点 3、**[Polaris]**；校验规则是 **[决定]** |
| **印象**：住户对玩家或别人的印象必须引用自己经历过的事；不同住户的印象可以互相矛盾，Harness 不去统一 | **[讨论]** 观点 1 |
| **按人拆开**（v1.1，v1.2 加了 Aisyah 一家）：林家、Mei 家、Aisyah 一家（`split: true`）每个成员是一个角色（`weiming`、`huiling`、`junhao`、`wangmei`、`jianguo`、`xiaoyu`、`rahman`、`aisyah_kassim`、`nurul`、`hafiz`、`mak_esah`），各有位置、印象、经历，成员可以有自己的 `goal`、`view`、`voice`、张力；陈阿姨、Kumar 和工友仍是一户一个角色（id 就是户名）。拆开的户名不能当一个人用（不能 `speak`/`impression`/摆进场景）。满意度、需求、障碍、揭示记录仍按户算，一户人共用回传上限；回传记录多一个 `by` 写是谁提议的。太小的孩子到 `talks_from` 那年才会说话 | 另一个 AI 的修订意见要求夫妻各有认知和秘密 → **[决定]** |
| **秘密谁知道、什么时候成立**：秘密可以带 `holder`，只有他自己能说出来，家里其他人的视角里也没有它；没有 `holder` 的是全家都知道、只瞒外人的；`known_to` 写别人家里也知道的人（王美洗碗，Aisyah 和 Kumar 知道），他们的视角里有，但只有本家的人能 `reveal`；`from` / `to` 写这件事从哪年到哪年成立，不到年份不能说（伟明 1998 年才被裁，Priya 2008 年才上大学）。旧事可以带 `members`，只有这几个人知道（1964 年的事只有陈阿姨和老祖母） | **[决定]**；`from` 是 Kumar 时间线问题（**[Polaris]**）带出来的 |
| **张力倾向**：每对张力一个 -3（偏 a）到 3（偏 b）的倾向，一次挪一格，要引用比上次更新的事件；只靠对话的话每个十年最多挪一次。倾向记在有张力的人身上：林家共同的"往上走 ↔ 留下来"记在户上（`tension_holder: "family"`，家里任何一个人经历过的事都能引用），伟明、慧玲各记自己的；Mei 家的核心张力记在王美身上 | 沿用 **[V0.1]**"策略变化不能只靠对话"；数值是 **[决定]** |
| **揭示**：障碍、秘密、旧事只能由本人当着玩家说出（角色输出的 `reveal`），GM 不能替他说 | **[V0.1]** 揭示门的思路，**[DS-team4]**"不拜访不知道障碍" |
| **设定门**：不能把设定、更不能把张力直接说出来。台词、旁白、场景说明、行动描述（玩家看得到、由模型写的文字）都要过三条检查：不能出现元语言（张力、锚点、设定、人设……）；同一段话里不能同时出现某户张力的两头；不能照抄设定原文（中文连续 12 个字、英文连续 8 个词）。原作台词可以说；秘密和旧事说出来之后可以照说。被拦下的不写入、不扣政策点 | **[Polaris]** 硬约束；三条检查是 **[决定]**，思路沿用 **[V0.1]** 揭示门 |
| **主动**：住户可以走到你旁边搭话；不在同一张图就记成"有人敲门" | **[讨论]** 观点 2 末尾、**[Polaris]**（替代信件） |
| **进度钟**：4/6/8 格；推进或倒退一格都要引用比上次更新的事件；满格后果自动变成一条事件，必须发生、只发生一次；满格的钟不能撤；建了对口设施，相关的钟解除 | Dungeon World Fronts、Blades in the Dark 进度钟（**[讨论]** 观点 4）；规则是 **[决定]** |
| 钟种子：原作信件里的冲突改写成钟（智能中心 → 陈阿姨不再下楼；收紧配额 → Aisyah 家卖不掉房；涨租 → 熟食中心吃不起；清理 → 长桌没地方摆；托儿排队；午后高温） | **[DS-team4]** 信件条件 → **[决定]** |
| 时间只能往前走；V0.2 不能自己走出这个十年，进入下一个十年由游戏端推进；跨十年时账本清零、留出纪要位置 | **[决定]** |
| Mei 一家 1994 年搬来（v1 是 1992 年，按最低居住年限改）；Kumar 2014 年回国、Murugan 接班；林俊豪、Nurul、老祖母按年份离开或过世 | **[决定]** + **[史]**，见 V0.2_WORLD |

## 6. 满意度回传

**[Polaris]**：可以回传，但幅度不能太大，不能只靠花言巧语让住户支持政策；政策对谁有负面影响，那户的满意度照样大幅下降。

具体数值是 **[决定]**，**[Polaris]** 同意先用、跑了再调：

| 来源 | 每户每个十年 |
|---|---|
| 纯对话 | 最多 **+2**，最低 **−5**（说谎被识破、冒犯、失约可以掉得更多） |
| 玩家的实际行动（`community_action`，扣 1 政策点） | 需求对口最多 **+5**，不对口最多 **+1**；最低 **−5** |
| 合计 | **+6 / −6** |
| 本十年因游戏端掉了 X 点 | 正向合计不超过 **⌊X/3⌋** |

- 方向和幅度由住户自己提议（角色输出的 `satisfaction`），Harness 只裁剪，不替住户决定。
- 只能引用这个十年里、这户经历过的事件。引用了针对他的行动事件就按"行动"算，否则按"对话"算。
- **已知张力**：受过轻微伤害的人（比如 X = 4）本十年最多只能补回 1，反而比没受伤害的人（最多 6）少。我的理解是"这个十年他的心情被这件事主导了"，但这个边界值得跑了再看。

## 8. 对外接口

`createSession({ lang, seed })` · `pushGameEvent(event)` · `propose({ by, ops })` · `gameAction(verb, ...)` · `advanceDecade()` · `getView(perceiver)` · `exportLog()`

计划里写的 `act(text)` 留到 M2：它会在 `propose` 之上跑 GM 调用和角色输出调用。接入真游戏时，用游戏发来的事件替换模拟器的输出即可。

## 9. 还没做 / 已知局限

1. ~~没有界面、地图渲染和模型调用~~ M2 做了界面、平面图、GM 和住户的调用；规划调用、纪要调用还没写（M3）。

3. 日历简化成每月 28 天、每天 6 个时段。
4. 所有数值（满意度、上限、政策点、钟格数）都没有经过游玩测试。
5. 设定门是关键词和原文比对，**意译能绕过去**（比如"我盖的楼，现在没人记得我了"不会被拦）。它防的是最直白的点题和照抄；更细的要靠提示词（`DISCLOSURE_NOTES`），M2 被拦下时会要求重写一次，是否再加一次模型自查，跑了再看。
6. 陈阿姨的过世、Kumar 的回国目前只体现在数据和人生阶段里，什么时候、怎么发生，要等规划层（M3）。
7. 拆开以后每户有好几个角色，M2 的提示词要决定是每人一次调用，还是一户一次调用、按人分开输出。按"不一定每人一个 Agent"的意见，我倾向后者，但私有信息按人给。

### 11.4 一轮怎么走 **[V0.1] + [决定]**

1. 玩家说一句话：对住户说（可以先点一个人，"对着"他说），或者对 GM 说想做什么、问一句（10-29 起，见 11.10）。
2. GM 调用：看平面图上谁在、谁挨着玩家、今天是什么日子，提出操作（叙述、确立细节、检定、推进时间、花政策点的行动……）和这一轮由谁回应（最多两个）。Harness 一条条校验；没通过的把原因给 GM，重给一次那几条，还不过就丢掉。
3. 花政策点的行动先问玩家确认，确认了才扣点并报给游戏端；不确认就写"你想了想，这次没有去做"。
4. 推进时间放在行动之后；时间过了，没在跟玩家说话的人按日程走动。
5. 回应的人各一次调用，同时跑，每人只看到自己的视角（自己知道的事、自己经历过的事）。台词过不了设定门就重写一次；还不过，这句话就不说，只留动作，都没有就由代码写"某某看了你一眼，没有说话。"
6. 台词里有读的人看不懂的方言或外语时，住户自己在同一次输出里给整句翻译（`gloss`），显示在台词下面；没给、这句话又看着难懂，GM 再补一句翻译（多一次调用，见 11.8）。
7. 住户提议的满意度变化按第 6 节的上限裁剪，报给游戏端。

**住户不知道自己的以后** **[Polaris 10-28]**。原来的做法是把整段来历给住户，再叮嘱"来历里以后的事还没发生"，这挡不住模型；现在改成根本不给：

- 来历、旧事、张力的推力这些文字，开局写的是 1989 年时的样子，以后才发生的段落放在 `later` 里，带年份（`world.js` 的 `textAt`）。提示词按当前年份截断，没到那一年的段落 GM 和住户都拿不到。设定原文没有改，只是拆开了：俊豪上小学、Nurul 进理工学院、Kumar 的女儿出生、Shohel 来、2013 年骚乱、俊豪跟 Kumar 学补车胎、林家孩子去 Aisyah 家吃糕。做英文版时又逐句读了一遍，补拆了几处没写年份的：王美"二三十年后新加坡熟了"（2009 年起）、"慢慢有人专门来请教华文"（1999 年起）、晓雨"两边都说得像本地人"（1999 年起）；Kumar 1990 年才有女儿，所以 1989 年他的目标是"多攒点钱寄回家"，宿舍里看的是"家里寄来的照片"。
- 人生阶段的文字和张力的走向（`about_from` 之前）不给住户；秘密按 `from`/`to` 给。
- 推力写成"要是遇上这些事"，免得模型当成已经发生。
- 测试把 1989 到 2018 年每一年、每个会说话的住户的提示词都扫一遍，不能出现比今年晚的年份；另外逐条查了没写年份的以后的事（11.5）。
- GM 仍然知道这个十年的大方向（人生阶段），那是 GM 安排伏笔要用的，但同样拿不到以后十年的段落。

另外，俊豪、晓雨、Hafiz、Nurul、Mak Esah 原来没有自己的说话方式，提示词里用的是全家那一条（六岁的俊豪会说"能不能帮我们查一下托儿名单"，只说马来语的 Mak Esah 被写成说新加坡英语）；俊豪和晓雨还用了大人的目标。给这五个人补了一句说话方式，给两个孩子补了目标，都是照设定里已有的描述写的。

### 11.5 测试（M2 新加的 18 条）

棋盘（家具位置、每张图连通、门走得到）、日子（顺序、平日是工作日、每个时段每个人站得下且不重叠、晚上不能再等）、门（没搬来、没人在家）、提示词隔离（伟明被裁、慧玲推掉香港、1964 年的事、王美洗碗，各自只有该知道的人在该知道的年份知道；日子的背景不给住户）、住户不知道自己的以后（1989–2018 每一年扫年份，再逐条查没写年份的）、玩家身份、一轮的流程（GM 不能跳日子、行动要确认、设定门重写和兜底、回应的人、只能替自己说话）、离线演示的台词都过得了设定门、离线演示能把八个日子从头走到尾。

### 11.6 M2 已知局限

1. 离线演示的台词是写好的，只为把流程走一遍，看不出模型的表现。
2. 用真实模型时一轮是 2 到 5 次调用（GM 一次，回应的人各一次，加上可能的重给），会慢；没有做流式显示，因为文字要先过设定门。
3. 住户不会主动来找你（`initiate` 规则层有，M2 的住户输出里没开）；要等规划调用（M3）。
4. 日子是写死的八个；M3 起由规划调用来挑。
5. 英文版提前做了（11.7）。英文版的住户台词好不好，要用真实模型跑过才知道；离线演示的英文台词是照中文的意思写的，不是逐字翻译。

### 11.7 英文版 **[Polaris 10-28："先把英文版做了吧"]**

原计划在 M4，提前到这里做。

- **怎么选**：开始界面第一栏是语言（中文 / English），点了整局马上换；设置里也能换，换了从第一天重来。选择记在浏览器里。
- **哪些是两套**：界面上所有的字（`app.js` 里每句都经过 `t(中文, 英文)`，`index.html` 里写死的字由 `staticText()` 换掉）；GM 和住户的提示词（`prompts.js` 的英文函数和中文的一一对应，改一边要改另一边）；规则层退回给模型的理由（`harness.js` 的 `REASONS_EN` 按句式对照翻译）和一轮里的提示（`turn.js`）；系统旁白（"某某看了你一眼，没有说话"之类）；游戏端模拟器的报错；离线演示的台词和关键词；棋子上的字（英文用名字首字母）。
- **默认身份**：中文是何志强，英文是同一个人的写法 Ho Chee Keong（新加坡华人常见的方言拼法）。两种语言的身份分开存。
- **住户说什么话**：英文版里住户一律用英文写，本来说马来语、泰米尔语、孟加拉语、福建话、广东话、华语的，写成"像翻译过来的"，保留几个自己的词；中文版照旧用中文，可以夹方言和外语。
- **字体**：英文界面先用系统的拉丁字体，免得撇号、弯引号在中文字体里占一个全角。
- **测试（T10，9 条）**：英文局里每个日子、每个时段、玩家站在每张图上，GM 和在场住户的提示词里没有一个汉字；隔离（别人家的事、当天背景、以后的事）照中文版逐条测一遍；规则层和一轮流程退回的理由都是英文；离线演示的英文台词每人一一对应中文、都过得了设定门；英文离线演示把八个日子从头走到尾，玩家看到的每一行、每次调用的提示词和输出都没有汉字。另外用浏览器在电脑、手机、深色三种尺寸各走一遍：开始界面切到英文、走路、说话、确认花政策点、游戏端建设施、换日子、看三个页签、在设置里换回中文；页面文字、按钮提示、下拉选项里都没有汉字（语言按钮上的"中文"除外），没有报错，没有横向滚动。

### 11.8 每句话都看得懂 **[Polaris 10-29："每个人说话至少得让人看得懂。要不你让 gm 在每个人说完之后'翻译'一下？"]**

住户照设定会说广东话、福建话、马来语、泰米尔语、Singlish，原来只叮嘱"要让读的人看得懂"，离线演示里陈阿姨整句广东话、Mak Esah 整句马来语都没有翻译。现在：

- **住户自己先翻**：住户的输出多一栏 `gloss`，台词里有读的人可能看不懂的话，就把整句意思用平白的中文（英文版用英文）写在这里，只翻译、不解释。说话的人最清楚自己说了什么，也不用多等一次调用。
- **GM 兜底**：住户没给翻译、而规则层判断这句话看着难懂时，按 Polaris 说的，请 GM 补一句翻译（多一次调用，状态栏写"GM 在把听不懂的话翻出来"）。判断是粗略的：中文局里有广东话的字（嘅、咗、佢、冇、唔识……），或者去掉人名地名后拉丁字母比汉字多一倍以上；英文局里有汉字，或者四成以上的词是马来语。新加坡英语的语气词（lah、leh、lor）不算。
- **显示**：翻译写在台词下面一行，小一号、浅一点，前面标"意思是："（英文版 "Meaning:"）。"你知道的事"里引用的原话也带着翻译。
- **翻译同样过设定门**，不能借翻译点题或照抄设定。GM 只能给住户说的话补翻译，补过一次就不能再改。
- **模型之间**：别人听到的那句话在提示词里带着翻译（"陈阿姨：……（意思是：……）"），GM 和其他住户也不会误解。
- **测试（5 条）**：判断难懂的规则；规则层存翻译、翻译过设定门、GM 补翻译的权限；提示词里要求给翻译、别人听到的话带翻译；一轮里给了翻译就不多调用，没给而难懂就由 GM 补，普通的话不翻译；离线演示里看着难懂的台词都带翻译。两种语言的离线演示走完八个日子，难懂的话都带着翻译。

### 11.9 token 数和上下文用量 **[Polaris 10-29："得加个token数计算和上下文计算的功能"]**

- **数从哪来**：填 API Key 的两种接口在回答里报 token 数（Anthropic：`usage.input_tokens` / `output_tokens`，加上缓存的两项；OpenAI 兼容：`usage.prompt_tokens` / `completion_tokens`），有就用，算准确数。claude.ai 网页内置的 Claude 不报（sample 能力只回文字），离线演示没有模型，这两种按字数估算，界面上带"≈"。
- **怎么估** **[决定]**：Claude 按一个汉字（含全角标点）约 1.1 个 token、其余字符约 3.5 个一个 token；DeepSeek 等 OpenAI 兼容接口按 DeepSeek 文档的一个中文字符约 0.6 个、一个英文字符约 0.3 个。Claude 的汉字比例没有官方数，取的是一个公开实验里的例句（19 个汉字 21 个 token），所以只用来看大小，差一两成很正常。有准确数的调用会同时记下估算，写字板里显示"实际是估算的几倍"，以后可以拿来校准。
  来源：DeepSeek API 文档 token 用量页（api-docs.deepseek.com/zh-cn/quick_start/token_usage）；jangwook.net 的多语言 token 实验（用 Hugging Face 上的 Claude 分词器离线数的）。
- **上下文怎么算**：每次调用都是单独的一问一答，不带之前的对话，所以一次调用的"上下文"就是这次发出去的全部提示词，看它占模型上下文窗口多少。窗口按模型名查（`tokens.js` 的 `WINDOWS`：Claude 5 系列和 Opus / Sonnet 4.6 以后 1M，Haiku 4.5 和更早的 200K，DeepSeek 128K；认不出的模型只记 token 数，不算占比）。网页内置的 Claude 另有一次最多发多少字节的上限（`sample.limits().maxPromptBytes`，现在是 256 KB），这个比窗口先到，所以网页内置的那种主要看字节。离线演示按网页内置的默认模型（claude-sonnet-5-5）算占比。
- **在哪看**：输入框下面写这一轮调用了几次、共多少 token；写字板"调用记录"最上面是整局合计（几轮、几次调用、输入、输出、最大的一次占多少），下面按轮分组，每次调用写输入、输出、占上下文多少；展开"提示词和原始输出"能看到提示词里各部分（按 `## 标题` 分段）大约多少 token。导出记录里也带上每次调用的用量（不带提示词全文）。一轮中途出错时，已经发出的调用照样记下，标"没跑完"。
- **现在的大小**（离线演示第一天早上，按估算）：GM 一次约 7,000 token（中文）/ 6,200（英文），其中"住户（只有你看得到）"一段占一半多；住户一次约 2,700 / 2,400，最大的是"说话的规矩"。合起来一轮约 1 万 token，占 1M 窗口不到 1%，占网页内置 Claude 的字节上限约 8%。"最近发生的事"会随一天变长。
- **测试（8 条）**：两种估算比例；两种接口的用量换算；按模型名找窗口；一次调用用准确数、各部分对得上、网页内置的看字节；合计（准确和估算分开、最大的一次、实际比估算）；离线演示一轮每次调用都有用量、英文局的分段标题没有汉字；报用量的接口用准确数、出错也交出已发的调用；导出带用量。

### 11.10 只说话、分两路；先操作，后叙述 **[Polaris 10-29 试玩之后]**

10-29 的两局试玩（中文局陈阿姨下棋，英文局 Aisyah 家）暴露的问题有同一个根：文字和状态是两条线，文字说了，状态没跟上；玩家的输入也不分是对谁说的。问题清单和方案在项目文件 `research/V0.2-试玩问题清单.md` 和 Claude Doc《V0.2 试玩问题总结与修改方案》。下面标 **[Polaris]** 的是 Polaris 定的，标 **[决定]** 的是方案里我推荐、Polaris 让我先按推荐做的，都可以再调。

**玩家只说话，分两种对象** **[Polaris："用户的语言全都视为对话，要不然作为游戏人物跟 npc 对话，要不然是作为玩家身份跟 gm 说话"]**

- 输入框左边是一个两段的开关：「对着 某某 / 说出口」和「对 GM」 **[决定]**。默认：点过的人、或者身边只有一个人，就对他说；身边有人就说出口；身边没人就对 GM **[决定]**。选了「对 GM」会一直保持，直到点了别人、换了地图或者切回来。
- 对住户说：记成 `player_input`（带 `to`），同一张图上的人都听得到。这一轮 GM 只决定世界怎么接（谁开口、周围有没有变化），**不能**替玩家花政策点、挪玩家、出戏回答，用了就退回（`turn.js` 的 `ONLY_WHEN_ASKED`）。
- 对 GM 说：记成 `player_to_gm`，只有玩家和 GM 知道，永远不进住户的经历和提示词。GM 能做就做：先发操作，再用第二人称写结果；提问、要提示用新的 `gm_reply` 出戏回答，只给玩家看。GM 什么给玩家看的都没写时，代码补一句"GM 没听明白"。
- **GM 把执行后的结果告诉住户** **[Polaris]**：住户看到的是 GM 写的那句结果（"你在棋桌对面坐下，把红子摆好"），不是玩家的请求。`narrate` 可以带 `noticed_by` 指定谁注意到了，不写就是同一张图上的人都看到 **[决定]**。
- 界面上对 GM 的话和 GM 的回答是灰色小字，前面有"对 GM""GM"的小标签。

**先操作，后叙述** **[决定]**

- 新操作：`leave`（离开地图，去处记在 activity，在场的人看到"某某离开了（去巴刹）"）、`set_activity`（只改在做什么）、`place_prop` / `remove_prop`（一件一件地摆上、拿走；固定家具拿不走）、`extras`（无名配角，见下）、`gm_reply`。
- 家具上不能站人，物件不能压着家具。原来 `set_scene` 和 `move` 不查这个，中文局里陈阿姨就坐在了棋桌那一格上；4 条老测试也把人摆在了棋桌上，一起改了。
- **无名配角上地图** **[决定]**：GM 写"三个老伯"，就先用 `extras` 摆一组（"老伯 ×3"），画成一个灰色小棋子，写人数，名字在下面；只占格子、不说话，也能 `leave`。一张图最多 4 组，换一天清掉。点它会提示是谁、在做什么。
- **事实和事件分开**：提示词写明 `establish_fact` 只定之后一直成立的事，一次性的动作用操作加 `narrate`（中文局里 GM 把"陈阿姨要走"记成了永久事实 `chen.leaving_habit`）。
- GM 提示词的地图一节列出这张图上能摆的物件 kind，配角也列在"这里有谁"里。

**住户只拿到自己所在环境和自己家** **[Polaris："住户应该只有自己房子的信息，和自己所在环境的信息"]**

- 住户提示词的"现在"一节换成场景块，和 GM 的地图一节用同一段代码生成（`prompts.js` 的 `layoutLines`），按视角取舍（`harness.js` 的 `getView(...).surroundings`）：所在这张图的底图、门、家具、摆出来的东西，自己在哪、在做什么，在场的人和配角各在哪、在做什么，玩家在哪、隔几格、够不够得着；自己家的布置（人不在家也有）；这两处、而且是自己在场时定下的细节。
- 别人家的、自己不在场时的事都不给。另外补了一处：GM 在住户面前确立"别人家"的细节（比如在楼下定了"林家新买了彩色电视"），原来在场的人都算"经历过"，现在只有眼前和自己家的细节进住户的经历（`knowsDetail`）。秘密、进度钟、满意度照旧不给。
- 住户提示词写明：旁白里的"你"指玩家；act 里自己用名字、称玩家为"你"（英文局里 GM 说"you"、住户说"him"）；只能碰到一格以内的人和东西。

**住户自己走动、离开** **[决定：两者都做，住户自己的 move 优先，自动靠近兜底]**

- 住户输出多三栏：`move`（`{"x":5,"y":4}` 或 `"player"`，走到玩家旁边离自己最近的空位）、`doing`（之后在做什么）、`leave`（去哪）。顺序是先走过去，再说话、做动作，最后才离开。住户只能在自己所在的图上走，去别处用 `leave`。
- 兜底：玩家对着他说话、他离玩家超过一格、自己又没写 `move` 或 `leave`，就替他走到玩家旁边（RPG Maker 的常见做法）。

**轻检查** **[决定]**

- GM 这一轮的叙述里，同一句话出现在场者的名字（住户或配角）加"走了、离开、散开、往……走去"之类的词（中英文各一组，带否定词排除），这个人却还在地图上：退回给 GM，只要求补 `leave`，不重写叙述。补了还对不上就放行，在调用记录里记一条 `check`。
- 住户的 act 写自己走了却没写 `leave`：这句先扣下，和 `leave` 一起重写一次；两次都不写，就把原句放出来，记一条 `check`。
- 关键词检查有误报和漏报，只兜底，主要靠前面的操作和提示词。

**代码审查后补的**（四个角度各一个审查，每条发现再由另一个去复现，12 条复现成立，都改了）：

- 模型漏写坐标（只改配角在做什么、物件没写位置）会让规则层抛错、整轮中断：坐标不是整数就当作地图外；改配角时没写的栏位照旧；GM 和住户的每条操作都包了一层，规则层哪里没防到也只算这一条没通过。
- 配角、住户（GM 挪的和自己走的）、摆场景的人都不能站在门上，不然玩家出不去。
- 住户的 `leave` 一律最后做：先说话、重写、兜底的那句反应，最后才离开。原来只写 `leave` 的住户会在"离开了"之后再"看了你一眼"，话被退回时重写也说不出来（人已经走了）。
- 掷骰只有玩家看得到，在场的人看到的是分支里 `narrate` 写的结果（原来掷骰的原因，也就是玩家的请求和数字，在场的人都"看到"）。检定分支里只能放结果（narrate、establish_fact、走动、离开、物件、配角），花政策点、推进时间、出戏回答、挪玩家都不能藏在分支里绕过确认。
- 对 GM 说的事没做成（政策点用完、玩家不确认、规则不让）的那几句只给玩家看。
- 轻检查的误报：叙述写"朝你走了过来""走到你旁边"不算离开；这一轮被 `move` 挪过的人不退回；退回的话改成"真的离开了就补 leave，只是走动就 move，都不是就输出空的"，误报也只多一次调用。英文去掉了 `heads for`、`left the`。住户的 act 带 `move` 时也不查。
- 提示词写明配角称呼不超过 12 个字、不能站在门上，英文的例子改短。
- 离线演示里 GM 只出戏回了一句时，身边的人不接话。
- 界面上手动选的"说出口 / 对 GM"只在选的那张图上算数，换了一天、被 GM 挪到别处都回到默认。
- 另外一条审查认为是老问题、不算这次的：住户是玩家说完话才被 GM 叫来的，原来"这一轮"一节会塞进玩家的原话，现在照实写"这一轮你没看到、没听到什么新的事"。

**第二轮审查后补的**（只看上面的修补，10 个审查/复现，4 条成立；另外两条复现没跑完的自己核实了，也补上）：

- 自动靠近把 act 的检查关掉了：住户离玩家远、被点名、act 写"回家去了"却没写 `leave`，代码替她走过去的那一步被当成"她自己写了 move"，就不退回了。现在只认她自己写的 `move`；act 说要走时，也不先替她走过去。
- "走近"的排除太宽：「陈阿姨朝你摆摆手，转身走了」「向你道了别，离开了棋桌」「反应过来」「递过来」整句都被当成走近，查不出离开。现在走近只认"往这边走"（朝你走、走了过来、走到你旁边），而且一句话按逗号（英文还有 and、then）拆成小句逐个看；没写名字的小句算前面最近提到的人；「陈阿姨离开了棋桌，伟明走了过来」走近的是伟明，不挡住陈阿姨。名字也认简称（伟明、Wei Ming、Kumar）。
- "这一轮挪过位置的不退回"改成按位置比：只改配角人数或在做什么、没挪的，叙述说"散了"照样退回；检定分支里 `move` 过的、`set_scene` 摆过的人也算挪过。
- 检定的分支写成一个对象（不是列表）：原来骰子掷完才出错，重给一次就掷了两次。现在分支不是列表就在掷骰前退回；分支里某一条出错只算那一条。
- 门口只剩一格能进出时（陈阿姨家、办公室、宿舍、各家的门），那一格也不能让住户、配角站，自动靠近也不挑那一格；楼下这种门边有两格的，占一格可以，两格都占就不行。GM 提示词里写了这一条。

**测试（30 条，`tests/talk.test.js`）**：两种输入的事件和感知（对 GM 的话不进住户的视角和提示词，住户这一轮什么都没看到时照实说）；对住户说话的一轮 GM 不能花点、挪玩家、出戏回答，对 GM 说可以；对 GM 说却没回音时补一句；离线演示对 GM 说话（中英文）；`leave`、`set_activity`、`place_prop`、`remove_prop`、`extras`、家具不能站人、住户只能在本图走、`noticed_by`；住户场景块（家具、物件、人和配角的位置、和玩家隔几格、自己家、在场时定下的细节；没有别人家的东西、她不在场时的细节、秘密、进度钟、满意度），英文版场景块没有汉字；住户的 `move`、被点名时自动靠近、`leave` 在说话之后、act 说走了没写 `leave` 的重写和兜底；GM 叙述说走了没 `leave` 的退回、补上、没补时记一笔、否定句不退回；`leaveClaims` 中英文；新操作的退回理由都是英文。原来的测试改了几处：人不站棋桌（4 处），花政策点的行动、中英文两个离线演示里的"帮忙"改成对 GM 说（3 条）。两轮审查后补的 8 条和 5 条见上面两段。

**还没做**：act 里碰到玩家或东西但隔得远，现在只靠提示词和自动靠近，没有检查；玩家对 GM 说"我去七楼"时，GM 用 `move` 挪玩家（带 `map`）规则层允许，但界面上没有走过去的动画；配角不会自己按日程走，留到 M3 的规划调用。

### 11.11 上下文管理第一步：缓存、按时段取历史、GM 记得自己定的细节 **[Polaris 11-02："肯定是api key"]**

10-29 的上下文调研（实测：GM 一次约 1 万 token、住户约 5 千，一轮约 1.5 万，其中约七成每轮一字不差）定下分三步走，主力是填 API Key 的接口，所以先做提示词缓存。这一节是第一步，不加任何额外的模型调用。

- **提示词按多久变一次排** **[决定]**：缓存只认"从头开始一字不差"的那一截，所以不常变的放前面。
  - GM：系统提示（规则、操作说明）→ 玩家、住户设定、住户之间的旧事、钟种子（一个十年里基本不变）→ 今天的背景、早先定下的细节（一天里很少变）→ 最近发生的事（一轮一块，只往后加）→ 现在、地图、游戏端、局势钟、你对玩家的推测、这一轮（每轮都可能变）。原来"现在"和地图在住户设定前面，住户那 4 千 token 每轮都得重算。
  - 住户：系统提示（身份、规矩，不再放新闻和印象）→ 楼下这些年的新闻 → 你经历过的事 → 对玩家的印象、现在、场景、你家、这一轮。
  - 历史后面的东西每轮都没法命中（前面的历史每轮都在长），所以只有每轮都可能变的才放后面：GM 的推测、住户的印象差不多每轮都可能加一条，放在历史前面的话，加一条就把后面整段历史的缓存废掉。
- **缓存标记（Anthropic API）**：系统提示打一个，提示词里最多三个：GM 打在住户那一块、今天那一块、历史的最后一轮；住户打在新闻那一块（有新闻的话）和历史的最后一轮。一共不超过 4 个，是接口的上限。下一轮的历史只是在后面多了几块，上一轮最后一块的标记正好还在 20 块的回看范围里，能接着命中。缓存 5 分钟有效，读的价钱是正常输入的约 0.1 倍（Opus 5.5 是 0.05 倍），写是 1.25 倍。退回重写时多出来的那段说明单独一块，不打标记，前面照样命中。
  - DeepSeek 和其他 OpenAI 兼容接口是自动按前缀缓存的，不用标记，同样的排序也让它们命中。claude.ai 网页内置的 Claude 没有提示词缓存，排序对它没有影响。
- **历史按时段取** **[决定]**：原来取最后 30 条（GM）/ 20 条（住户），每多一条开头就往后挪一条，缓存永远接不上。现在取最新的时段加上它前面的时段（按事件发生的年月日和上午、下午、晚上算）；前面这部分不够 30 / 20 条就再往前补整段。最新的时段还在长，不算进这个下限，所以同一个时段里开头不动（审查时发现第一版把最新时段也算进去了，最新时段长到一定条数时开头会在时段中间往后跳）。超过 120 / 80 条才从前面剪，一次剪一整步（40 / 20 条；按审查时写的缓存模型算，步长从 20 / 10 加大以后，GM 每轮都定一个细节时住户的缓存读取比例从 68% 升到 78%）。所以开头只在进入新时段、或者攒够一步的时候断一次。这一轮的事只写在"这一轮"里，不在历史里重复一遍。历史的标题写"按时间先后"，不写"最近两个时段"：两个时段之间可能隔了好几个月。
- **GM 记得自己定的细节和推测**：原来 `establish_fact` 定下的细节只在事件里，滑出窗口 GM 就忘了，会和自己前面说的矛盾；`gm_hypothesis` 写了从来没人读。现在：还在窗口里的细节，历史里就有"确立：…"那一行；滚出窗口的列在"今天"那一块后面（最近 150 条，带定下的时间、是不是检定的结果）。这样这一块只在窗口开头往后挪时才变，定一个新细节不会废掉后面的历史缓存。GM 对玩家的推测（最近 5 条）放在最后一块。住户看不到 GM 的推测。
- **住户只拿到自己经历过的事**（10-29 的规矩）：历史里只放感知列表里有她的事件，别人家里的话、对 GM 说的话都不在里面；"这一轮"也只放她看到听到的。
- **记录**：每次调用记下这次看到了哪些事件（`seen`：历史里的、这一轮的、从哪条开始），以后查"她为什么不知道这件事"有据可查。用量多记缓存读、写两项：调用记录里写"缓存读 N，写 M"，合计写"有准确数的输入里 X% 是从缓存读的"；导出记录带 `cache_read`、`cache_written` 和每次调用的 `seen`。DeepSeek V4 的窗口按 1M 算。
- **还会断缓存的地方**（审查时找到的，没改）：秘密、障碍"已经跟玩家说过了"的标记和张力的倾向写在住户的系统提示和 GM 的住户那一块里。住户说出一个秘密、心里挪了一格，下一次就从头写一遍缓存。一个十年里只有几次，先不动。
- **还没量过**：容器里没有 API Key，真实的命中率要等你用自己的 Key 跑一局看写字板的合计。按字数估（离线演示第一天早上跑六轮）：GM 一次约 9,200 token，最后一个标记之前约 8,500；住户约 4,000，标记之前约 3,500。所以同一个时段里、5 分钟之内的下一轮，大约九成输入可以从缓存读，每轮新加的那一块写一次。住户的缓存按人算，同一个人 5 分钟内再开口才命中。
- **测试（11 条，`tests/context.test.js`）**：窗口取最新的和前面的时段、不够整段补、超上限按步剪、同一时段开头不动（包括审查时找到的那个例子）；中英文相邻几轮的系统提示和缓存的块一字不差、上一轮的历史是下一轮的开头、标记不超过 4 个；这一轮的事只出现一次、记录带 `seen`；住户的提示词里没有别人家的话和对 GM 说的话，GM 都看得到；住户的历史里（不只是这一轮）没有别人家定的细节、她不在时定的细节、她来之前玩家说的话；GM 定了细节下一轮"今天"那一块不变、滚出窗口的细节列出来、推测在最后一块、住户看不到推测；发给 Anthropic 的分块、重写时的说明、对不上就退回一整块；缓存读写的合计。`tests/tokens.test.js` 的用量格式改了两处；`tests/talk.test.js` 里英文场景块的检查改成看最后一块里的场景（场景挪到最后了，原来那样切就检查不到）；两条直接拼提示词的隔离测试先翻到下一轮再拼，历史那一段也一起检查（历史只取上一轮为止的事件，不翻的话历史是空的，查不出漏）。
- **审查**：四个角度（缓存能不能命中、住户隔离和中英一致、窗口和轮次、回归）各一个审查，每条发现再由另一个去复现。改了的：细节和推测、住户的印象挪出历史前面；窗口的下限不算最新的时段；历史的标题；英文场景块和两条隔离测试。另外按审查时写的缓存模型把剪窗口的步长加大了。
- **第二步**（和 M3 一起）：每人一份按天的日记和十年的编年（引用事件编号，规则层查谁看得到），印象设上限并合并，存档。**第三步**（试玩之后）：按在场的人裁 GM 的住户设定，浏览器里的关键词检索。
